# VILEORUF CRM — контракт архитектуры / продукта интеграций Day 5

## 1. Назначение и статус

Этот документ — действующий окончательный контракт архитектуры и продукта для **Day 5 — Integrations**.

Он фиксирует реализованный объём MVP и не допускает расширения кода, специфичного для провайдеров, работы с учётными данными, фоновых задач, хранения данных и UI за рамки согласованного продукта.

Разработка MVP Day 5 завершена. Этот контракт является источником истины для архитектуры и функциональности интеграций.

Приоритет интеграций остаётся следующим:

1. Gmail
2. Telegram
3. Google Calendar
4. WhatsApp

Внешние учётные данные, верификация провайдера, доступность публичного webhook, одобрение аккаунта или политика провайдера могут ограничить проверку в реальной среде. Приложение никогда не должно имитировать успешную работу реальной интеграции.

---

## 2. Принципы Day 5

1. Сохранять архитектуру модульного монолита.
2. Обращаться к внешним провайдерам только через сервисы/адаптеры интеграций.
3. Авторизация бэкенда остаётся источником истины.
4. Существующая история CRM остаётся долговечной при отключении или недоступности интеграции.
5. Сбой провайдера должен ухудшать работу интеграции, но не CRM в целом.
6. Контент, созданный AI, никогда не отправляется клиенту автоматически.
7. Пользовательский UI Day 5 локализован на русский, английский и испанский; русский остаётся языком по умолчанию/резервным.
8. Не создавать для этого MVP универсальную платформу интеграций или подсистему множественных аккаунтов.
9. Повторно использовать существующую инфраструктуру Celery/Redis там, где обоснована асинхронная работа с провайдером; не вводить ещё один брокер или микросервис интеграций.
10. Не утверждать, что операция провайдера успешна, пока результат не подтверждён провайдером.

---

## 3. Утверждённая модель корпоративных аккаунтов

MVP предусматривает ровно одно корпоративное подключение каждого типа интеграции:

- one corporate Gmail account;
- one corporate Telegram Bot;
- one corporate Google Calendar;
- one corporate WhatsApp Business account through WhatsApp Business Platform / Cloud API.

Индивидуальные Gmail-аккаунты и календари сотрудников, несколько ботов, несколько аккаунтов WhatsApp, владение подключениями на уровне тенанта и универсальное управление множеством аккаунтов не входят в Day 5.

Только `ADMIN` может подключать, переподключать, отключать интеграции и управлять их конфигурацией. `MANAGER` может использовать уже настроенную интеграцию только там, где существующая авторизация CRM разрешает базовую операцию над Client/Deal/Task.

## 4. Существующие доменные контракты, которые Day 5 обязан сохранить

### 4.1 Communication остаётся бизнес-историей CRM

`Communication` остаётся нормализованной дополняемой записью CRM о факте коммуникации.

Day 5 **не** превращает `Communication` в транспортную сущность провайдера.

Она по-прежнему представляет:

- Client;
- необязательный Deal;
- канал;
- направление;
- фактическое содержимое;
- фактическую временную метку коммуникации;
- существующую семантику записи CRM.

Идентификаторы сообщений, жизненный цикл провайдера, повторные попытки, ошибки провайдера, состояние синхронизации и дедупликация относятся к слою интеграций, а не к основному жизненному циклу `Communication`.

Центральное правило:

```text
Provider message != Communication
```

Для реальных каналов провайдера `Communication` создаётся только после принятия и сопоставления реального входящего сообщения с контекстом CRM либо после подтверждённого провайдером успеха реальной исходящей операции.

### 4.2 Существующая авторизация Communication остаётся базовой

- `ADMIN` может создавать/использовать коммуникации для любого валидного контекста Client/Deal.
- `MANAGER` может создавать/использовать коммуникацию уровня клиента для существующего Client и коммуникацию, привязанную к Deal, только для сделки, за которую менеджер отвечает.
- Проверки согласованности Client/Deal на бэкенде остаются источником истины.

Day 5 не должен ослаблять эти правила лишь из-за участия адаптера провайдера.

### 4.3 Task остаётся внутренней задачей CRM

`Task` остаётся внутренней рабочей единицей CRM с ответственным, сроком, необязательным контекстом Client/Deal и жизненным циклом `OPEN`/`COMPLETED`.

Событие календаря — другой бизнес-объект.

Утверждённая связь:

```text
Task != CalendarEvent
Task <-> CalendarEvent (optional explicit link)
```

Пользователь может явно создать событие календаря из Task. Завершение Task не должно автоматически удалять/отменять её событие календаря, а изменение/отмена события календаря не должны автоматически завершать Task.

### 4.4 EmailDraft остаётся рабочим документом до успешной отправки

Сохраняется существующее разделение Day 4:

```text
AIAnalysis = AI proposal/history
EmailDraft = employee-controlled working document
ExternalMessage = provider operation/lifecycle
Communication = actual CRM communication history
```

EmailDraft, созданный AI или вручную, никогда не отправляется автоматически.

После подтверждённой успешной отправки через Gmail отправленный EmailDraft становится историческим и **доступным только для чтения**. Его тему/тело должно быть возможно скопировать (например, «Копировать тему» / «Копировать текст» / «Копировать всё»), но историческое отправленное содержимое нельзя редактировать. Для нового последующего письма нужен новый черновик.

При неудачной отправке EmailDraft остаётся редактируемым и неотправленным. Неопределённый результат провайдера нельзя ложно помечать как `SENT`.

## 5. Границы интеграций по провайдерам

## 5.1 Gmail

### Утверждённое поведение MVP

- Один корпоративный Gmail-аккаунт, подключённый через Google OAuth.
- Исходящие email из CRM.
- Входящая синхронизация новых релевантных email.
- Точное сопоставление Client по нормализованному email-адресу.
- Детерминированная привязка Deal для ответов только там, где корреляция треда провайдера однозначно определяет сделку.
- Успешный исходящий email создаёт `Communication(channel=EMAIL, direction=OUTGOING)`.
- Сопоставленный входящий email создаёт `Communication(channel=EMAIL, direction=INCOMING)`.
- Существующий EmailDraft — основной управляемый сотрудником рабочий процесс черновика.

### Исходящий поток

```text
EmailDraft(DRAFT)
      -> explicit Send action
      -> authorization/contact validation
      -> ExternalMessage(PENDING)
      -> Gmail adapter/background job
      -> provider confirms success
      -> ExternalMessage(SENT)
      -> Communication(EMAIL, OUTGOING)
      -> EmailDraft(SENT, read-only, copyable)
```

Содержимое `Communication` — фактически отправленный текст, а не позднее отредактированная копия.

### Входящий поток

```text
Gmail sync/provider event
      -> authenticity/provider validation where applicable
      -> provider-message deduplication
      -> ExternalMessage(RECEIVED)
      -> exact Client match by normalized email
      -> optional deterministic Deal match by known provider thread
      -> Communication(EMAIL, INCOMING)
```

Если Client невозможно безопасно сопоставить, сохранять `ExternalMessage` несопоставленным; не создавать Client автоматически.

### Явные исключения Gmail

- полноценный клиент Gmail;
- управление папками/ярлыками;
- администрирование почтового ящика;
- импорт всей исторической почты;
- угадывание AI привязки Deal из текста email;
- автоматическая отправка черновиков AI.

---

## 5.2 Telegram

### Утверждённое поведение MVP

- Один корпоративный Telegram Bot.
- Входящие сообщения клиентов через интеграцию с Bot.
- Исходящие ответы сотрудников через Bot API.
- Архитектура входящего потока на основе webhook.
- Идентификатор пользователя Telegram у провайдера — предпочтительный стабильный идентификатор сопоставления после привязки Client; username не считается неизменной личностью.
- Сопоставленные входящие/исходящие сообщения становятся записями `Communication` только после соответствующего реального события/успеха у провайдера.

### Inbound flow

```text
Client -> Telegram Bot -> webhook
      -> Telegram adapter
      -> webhook authenticity validation
      -> deduplication
      -> ExternalMessage(RECEIVED)
      -> Client match
      -> Communication(TELEGRAM, INCOMING)
```

Если сопоставление Client недоступно или неоднозначно, сообщение остаётся несопоставленным для ручной привязки.

### Outbound flow

```text
CRM employee -> explicit Send
      -> authorization/contact validation
      -> ExternalMessage(PENDING)
      -> Telegram adapter/background job
      -> provider confirms success
      -> ExternalMessage(SENT)
      -> Communication(TELEGRAM, OUTGOING)
```

### Явные исключения Telegram

- личные Telegram-аккаунты сотрудников;
- управление группами/каналами Telegram;
- полноценный Telegram-клиент внутри CRM;
- автоматические ответы AI;
- автоматическое создание Client из произвольных входящих пользователей Telegram.

---

## 5.3 Google Calendar

### Утверждённое поведение MVP

- Одно корпоративное подключение Google Calendar через Google OAuth.
- Выделенная сущность CRM `CalendarEvent`.
- Явное создание событий из контекста Client, Deal или Task.
- Синхронизация создания/обновления/отмены событий, созданных CRM.
- Хранение идентификатора события провайдера и внешнего URL Google Calendar, если доступен.
- Отображение состояния связанного события в релевантном контексте CRM.
- Возможность открыть синхронизированное событие в Google Calendar.

### Утверждённая модель связей

`CalendarEvent` может иметь необязательные ссылки на:

- Client;
- Deal;
- Task.

Согласованность Client/Deal должна оставаться под контролем бэкенда.

### Поток создания

```text
Client / Deal / Task
      -> explicit Create/Add to calendar
      -> CalendarEvent(PENDING)
      -> Google Calendar adapter/background job
      -> provider confirms success
      -> CalendarEvent(SYNCED)
      -> provider_event_id + external_url stored
```

Сбой провайдера приводит к безопасному состоянию ошибки без изменения жизненного цикла несвязанных Task/Deal/Client.

### Явные исключения Calendar

- замена Google Calendar интерфейсом календаря CRM;
- календарь месяц/неделя/день по адресу `/crm/calendar` в Day 5;
- импорт полной истории календаря пользователя;
- рассмотрение каждой Task как события календаря;
- автоматическое завершение Tasks по состоянию календаря;
- сложные процессы повторений.

## 5.4 WhatsApp

### Целевая интеграция

Утверждённая цель — WhatsApp Business Platform / Cloud API. Автоматизация потребительского/личного WhatsApp не входит в контракт.

### Утверждённое поведение MVP при доступной конфигурации провайдера

- один корпоративный WhatsApp Business-аккаунт;
- входящие сообщения через webhook провайдера;
- исходящие сообщения сотрудников через утверждённый путь адаптера/API;
- сопоставление Client по нормализованному идентификатору WhatsApp/телефона, когда это безопасно;
- успешные сопоставленные сообщения становятся `Communication(WHATSAPP, ...)`;
- операции webhook/провайдера дедуплицируются.

### Правило внешних ограничений

Если верификация Meta Business, учётные данные, конфигурация телефона, шаблоны/политики, требования к публичному callback или другие предварительные условия провайдера препятствуют работе в реальной среде, реализация может завершить утверждённые адаптер/интерфейс, хранение, валидацию, тесты и документацию по настройке, но обязана указать, что провайдер **не проверен в реальной среде**. Нельзя отображать или документировать фиктивно успешную реальную интеграцию.

### Явные исключения WhatsApp

- автоматизация потребительского WhatsApp;
- несколько аккаунтов WhatsApp;
- подсистема кампаний/массовых маркетинговых рассылок;
- универсальная платформа управления шаблонами сверх минимума, строго необходимого для утверждённой операции провайдера;
- автоматические ответы AI.

## 6. Модель хранения

Day 5 вводит минимальную границу хранения интеграций. Точные названия SQLAlchemy могут следовать соглашениям репозитория, но семантический контракт ниже фиксирован.

## 6.1 IntegrationConnection

Назначение: безопасные, не содержащие секретов метаданные и жизненный цикл одного корпоративного подключения провайдера.

Минимальные семантические поля:

```text
id
provider
status
display_name
external_account_id / safe external identifier (optional)
external_account_email / provider-safe display identifier (optional)
connected_at (optional)
last_success_at (optional)
last_error_at (optional)
last_error_code (optional)
created_at
updated_at
```

Значения провайдера:

```text
GMAIL
TELEGRAM
GOOGLE_CALENDAR
WHATSAPP
```

Значения статуса подключения:

```text
DISCONNECTED
CONNECTING
CONNECTED
ERROR
```

База данных должна обеспечивать инвариант MVP: одно корпоративное подключение на провайдера.

`IntegrationConnection` не должен раскрывать учётные данные в открытом виде через обычные API-схемы.

## 6.2 ExternalMessage

Назначение: жизненный цикл провайдера/интеграции для сообщений Gmail, Telegram и WhatsApp.

Минимальные семантические поля:

```text
id
integration_connection_id
provider
provider_message_id (nullable until known for outbound)
provider_thread_id (optional)
client_id (optional)
deal_id (optional)
communication_id (optional)
direction
status
sender_identifier
recipient_identifier
subject (optional)
content
provider_created_at (optional)
received_at (optional)
sent_at (optional)
last_error_code (optional)
created_at
updated_at
```

Утверждённые значения статуса жизненного цикла:

```text
PENDING
SENT
RECEIVED
FAILED
UNKNOWN
```

`UNKNOWN` означает, что провайдер мог принять исходящую операцию, но CRM не может безопасно подтвердить результат. Её нельзя незаметно повторять или представлять как отправленную.

Реализация должна обеспечить ограниченное провайдером правило уникальности/идемпотентности, эквивалентное предотвращению повторной обработки одного сообщения провайдера для одного подключения.

Не создавать для MVP отдельные доменные таблицы GmailMessage, TelegramMessage и WhatsAppMessage.

## 6.3 CalendarEvent

Назначение: представление CRM и жизненный цикл синхронизации с провайдером для явно созданного события календаря.

Минимальные семантические поля:

```text
id
integration_connection_id
client_id (optional)
deal_id (optional)
task_id (optional)
provider_event_id (optional until synchronized)
title
description (optional)
start_at
end_at
timezone
status
external_url (optional)
last_synced_at (optional)
last_error_code (optional)
created_by_user_id
created_at
updated_at
```

Утверждённые значения статуса:

```text
PENDING
SYNCED
CANCELLED
ERROR
```

Отмена у провайдера должна сохранять историческую запись CRM, а не физически удалять её.

## 6.4 EmailDraft send-state extension

Day 5 может минимально расширить существующее хранение `EmailDraft`, чтобы различать как минимум:

```text
DRAFT
SENT
```

и сопоставлять успешно отправленный черновик с полученной фактической коммуникацией/операцией провайдера по потребности реализации.

EmailDraft со статусом `SENT` неизменяем как историческое содержимое, но остаётся доступным для чтения и копирования.

Ни одна функция Day 5 не может переписать отправленный черновик так, чтобы он перестал соответствовать фактически отправленному.

## 7. Правила идемпотентности и создания Communication

### 7.1 Глобальный инвариант

Одно внешнее сообщение/событие провайдера должно создавать не более одного соответствующего `ExternalMessage` и не более одного результирующего `Communication` для данного факта провайдера.

Повторная доставка webhook, повторная синхронизация Gmail, повторная попытка воркера, браузера или дублирующий callback провайдера не должны дублировать историю коммуникаций CRM.

### 7.2 Исходящие

```text
explicit user action
      -> ExternalMessage(PENDING)
      -> provider operation
```

При подтверждённом успехе:

```text
ExternalMessage(SENT)
      -> create exactly one Communication(OUTGOING)
      -> link records
```

При подтверждённой ошибке:

```text
ExternalMessage(FAILED)
      -> no Communication
```

При неопределённом результате:

```text
ExternalMessage(UNKNOWN)
      -> no false SENT state
      -> no automatic duplicate resend
      -> no false Communication success record
```

### 7.3 Входящие

```text
provider event
      -> authenticity check
      -> deduplication
      -> ExternalMessage(RECEIVED)
      -> safe Client matching
```

Если сопоставление Client успешно, создать ровно один `Communication(INCOMING)`.

Если сопоставление не удалось, сохранять несопоставленный `ExternalMessage` и не создавать фиктивный Client и не угадывать Deal.

## 8. Сопоставление Client и Deal

### 8.1 Gmail

Сопоставление Client: точный нормализованный email-адрес.

Сопоставление Deal для входящего email разрешено только если детерминированная корреляция треда провайдера связывает ответ с более ранним исходящим сообщением, привязанным к Deal. Иначе использовать коммуникацию уровня Client.

### 8.2 Telegram

Предпочитать сохранённый пользовательский идентификатор Telegram провайдера. Username может помогать UI/настройке, но не должен считаться неизменным идентификатором провайдера.

### 8.3 WhatsApp

Использовать нормализованный утверждённый идентификатор WhatsApp/телефона, когда это безопасно.

### 8.4 Неоднозначность

- ноль совпадений → несопоставленный входящий ящик;
- одно безопасное точное совпадение → обработка на уровне Client;
- неоднозначные/множественные совпадения → несопоставленный входящий ящик;
- не использовать AI для угадывания Client или Deal из содержания сообщения в Day 5.

Для входящих сообщений Telegram и WhatsApp не выбирать Deal автоматически лишь потому, что у Client есть активные сделки.

---

## 9. Несопоставленный входящий ящик интеграций

Day 5 может добавить защищённый маршрут, например:

```text
/crm/inbox
```

Его назначение — **не** стать полноценным единым мессенджером. Прежде всего это операционная очередь входящих записей `ExternalMessage`, требующих ручной привязки Client или внимания.

Утверждённый рабочий процесс:

```text
unmatched ExternalMessage
      -> employee selects an existing Client
      -> backend validates link
      -> optional Deal remains unset unless explicitly and validly selected
      -> create exactly one Communication(INCOMING)
```

Day 5 не должен автоматически создавать Client из произвольного входящего трафика email, Telegram или WhatsApp.

## 10. Пользовательские рабочие процессы сообщений

### 10.1 EmailDraft сделки

Существующий UI EmailDraft сделки расширяется явным поведением отправки через провайдера.

Перед отправкой показывать понятное подтверждение как минимум с получателем и темой. UI не должен сообщать «Отправлено», пока операция лишь поставлена в очередь/ожидает выполнения.

После успеха:

- черновик показывает `SENT`;
- содержимое доступно только для чтения;
- остаются доступны «Копировать тему» / «Копировать текст» / «Копировать всё»;
- фактическая `Communication` появляется в истории коммуникаций Deal/Client.

### 10.2 Telegram и WhatsApp

Использовать существующий контекст коммуникаций Client/Deal, а не создавать отдельные полноценные приложения-мессенджеры.

Действие отправки через реальный канал должно вызывать интеграцию провайдера. UI не должен напрямую создавать фиктивную исходящую `Communication` реального канала до успеха у провайдера.

`MANUAL` остаётся способом вручную записать факт внешней/офлайн-коммуникации там, где это уместно.

### 10.3 Доступность интеграции

UI должен ясно различать:

- подключено и доступно;
- ожидает/подключается;
- отключено/не настроено;
- ошибка провайдера/конфигурации.

Отсутствующая конфигурация интеграции не должна приводить к сбою или блокировать обычную функциональность CRM.

## 11. Пользовательские рабочие процессы календаря

Утверждённые точки входа:

- контекст Client: создать событие;
- контекст Deal: создать событие;
- контекст Task: добавить в календарь.

Минимальная семантика формы:

```text
title *
date/start *
end *
timezone
description (optional)
Client (contextual/optional)
Deal (contextual/optional)
Task (contextual/optional)
```

После синхронизации показывать состояние события и действие `Open in Google Calendar`, когда есть внешний URL.

## 12. Учётные данные, OAuth, шифрование и секреты

## 12.1 Общее правило

Секреты никогда не попадают в исходный код, обычные бизнес-поля, журналы, отчёты о выполнении, проверки тестов, видимые в браузере API-полезные нагрузки или закоммиченные значения документации.

`.env.example` может содержать только не содержащие секретов заполнители.

### 12.2 Telegram / WhatsApp

В MVP статические учётные данные провайдеров, такие как токен Telegram Bot и секреты доступа/конфигурации WhatsApp, передаются через секреты окружения/развёртывания. `IntegrationConnection` хранит только безопасные метаданные/статус.

### 12.3 Google OAuth

Gmail и Google Calendar используют интерактивный OAuth для единого корпоративного Google-аккаунта/календаря.

Утверждённая модель:

```text
Google OAuth client credentials -> environment/deployment secrets
OAuth callback -> access/refresh token payload
              -> application-level encryption
              -> ciphertext persisted in PostgreSQL
Encryption key -> environment/deployment secret only
```

Ключ шифрования никогда не должен храниться вместе с зашифрованной полезной нагрузкой токена.

OAuth-токены в открытом виде могут существовать только временно в памяти процесса, когда это нужно для вызовов/обновления у провайдера. Их нельзя возвращать фронтенду или записывать в журналы/отчёты.

Day 5 не должен вводить универсальную платформу управления секретами. Использовать минимальную обоснованную реализацию шифрования и документировать любую новую зависимость до или при её добавлении.

### 12.4 Управление подключениями только для ADMIN

Только ADMIN может:

- инициировать подключение Google OAuth;
- переподключать/отключать Google;
- управлять/активировать конфигурацию интеграции Telegram;
- управлять/активировать конфигурацию интеграции WhatsApp;
- просматривать состояние подключения/настройки интеграций.

MANAGER должен получать отказ от бэкенда для endpoint-ов управления, даже при обходе навигации фронтенда.

## 14. Контракт webhook

Webhook — это входящий callback провайдера к границе интеграций CRM. Telegram и WhatsApp используют архитектуру входящего потока на webhook там, где это позволяют возможности/конфигурация провайдера.

Обработчики маршрутов webhook должны оставаться тонкими:

1. проверять подлинность провайдера через поддерживаемый им механизм проверки/подписи/секрета;
2. минимально валидировать форму полезной нагрузки;
3. применять/сохранять достаточные идентификационные данные провайдера для идемпотентности;
4. ставить в очередь или передавать более тяжёлую обработку, когда уместно;
5. быстро возвращать подходящий ответ.

Неаутентифицированный/непроверенный callback провайдера не должен создавать `ExternalMessage`, `Communication`, Client или иную бизнес-запись CRM.

Повторная доставка валидного webhook должна быть безопасной и идемпотентной.

Если локальная разработка не может принять требуемый провайдером публичный HTTPS webhook, это внешнее ограничение проверки в реальной среде, которое нужно документировать. Нельзя незаметно менять утверждённую production-архитектуру на несвязанную polling-схему лишь ради заявления об успешной проверке в реальной среде.

## 15. Фоновая обработка

Повторно использовать существующую инфраструктуру Celery + Redis.

Операции провайдера, которые не должны блокировать HTTP-запрос, могут использовать выделенную логическую очередь, например `integrations`, отдельную от существующей очереди `ai`, но в рамках того же развёртывания Celery/Redis.

Утверждённые кандидаты для асинхронной обработки включают:

- исходящую отправку Gmail;
- исходящую отправку Telegram;
- исходящую отправку WhatsApp;
- синхронизацию создания/обновления/отмены Google Calendar;
- более тяжёлую обработку входящих данных провайдера после быстрого принятия webhook;
- ограниченную входящую синхронизацию Gmail там, где она реализована.

Обычный CRUD настроек интеграций/чтение статусов остаётся синхронным, если сама операция провайдера не требует фоновой работы.

Фронтенд обязан отличать принятую/ожидающую работу от подтверждённого успеха у провайдера.

## 16. Семантика повторных попыток и ошибок

Ошибки провайдера должны нормализовываться за безопасными категориями ошибок приложения, а не раскрывать исходные тела ответов или учётные данные провайдера.

Примеры безопасных категорий:

```text
AUTH_REQUIRED
INVALID_CONFIGURATION
PERMISSION_DENIED
INVALID_RECIPIENT
RATE_LIMITED
PROVIDER_UNAVAILABLE
PROVIDER_ERROR
```

Точное внутреннее перечисление может уточняться во время реализации без раскрытия секретов.

### 16.1 Классы повторных попыток

**SAFE_RETRY**

Автоматическая повторная попытка разрешена только когда адаптер может установить, что она не вызовет небезопасное дублирующее действие у провайдера. Использовать ограниченное число попыток с возрастающей задержкой; Day 5 не должен вводить неограниченные повторные попытки.

**NO_RETRY**

Постоянные ошибки/ошибки конфигурации, такие как невалидные учётные данные, отказ в доступе или невалидный получатель, нельзя повторять бездумно.

**UNCERTAIN**

Если провайдер мог принять исходящую операцию, но CRM не может безопасно подтвердить результат, пометить `ExternalMessage` как `UNKNOWN`. Не отправлять автоматически повторно.

### 16.2 Семантика, видимая пользователю

Ожидающая работа: локализованный эквивалент `Sending...` / `Synchronizing...`.

Подтверждённый успех: локализованное подтверждённое состояние отправки/синхронизации.

Подтверждённая ошибка: локализованное безопасное сообщение об ошибке с действием повтора только там, где бэкенд объявил повтор безопасным.

Неизвестный результат: ясно сообщать, что результат не удалось подтвердить и его нужно проверить до следующей отправки.

Не показывать исходные тела ответов провайдера.

## 17. Поведение при отключении и недоступности провайдера

Отключение интеграции останавливает будущие операции провайдера, но не должно удалять исторические данные.

Сохранять:

- существующие записи `Communication`;
- историю `ExternalMessage`;
- историю `CalendarEvent`;
- историю отправленных EmailDraft.

Недоступность провайдера или невалидные учётные данные не должны делать недоступными Clients, Deals, Tasks, Pipeline, историю AI или другие несвязанные области CRM.

Существующая история коммуникаций остаётся доступной для чтения, когда провайдер отключён или работает с ухудшением.

По применимости проверить:

### 18.3 Покрытие API

По применимости проверить:

- ADMIN/MANAGER authorization;

- endpoint-ы отправки/создания/обновления/отмены;
- безопасные ответы с ошибками;

### 18.4 Проверка фронтенда/браузера

По применимости проверить:

- production-сборку;
- ключи RU/EN/ES и локализованные состояния;
- доступ ADMIN к настройкам интеграций и отказ для MANAGER;
- семантику UI для ожидания/успеха/ошибки;
- поведение EmailDraft при отправке/режиме только для чтения/копировании;
- привязку в несопоставленном входящем ящике;
- поток CalendarEvent: создание/открытие/обновление/отмена;
- работоспособность обычной CRM при отключённых/недоступных провайдерах.

Никогда не заявлять об успешной проверке, если она фактически не запускалась.

## 19. Условия проверки провайдеров в реальной среде

Моки/заглушки проверяют поведение приложения, но не доказывают интеграцию с реальным провайдером.

### 19.1 Проверка Gmail в реальной среде

Когда доступны учётные данные/доступ к аккаунту, проверить как минимум:

- реальное подключение корпоративного Google OAuth;
- один реальный тестовый исходящий email;
- подтверждённый успех провайдера → ровно одна исходящая Communication;
- один реальный тестовый входящий email;
- повторная обработка не дублирует входящую Communication.

### 19.2 Проверка Telegram в реальной среде

При доступной конфигурации Bot/публичного callback фактическая проверка включает как минимум:

- реальную конфигурацию Bot;
- одно реальное входящее сообщение;
- один реальный исходящий ответ;
- подтверждённые создание Communication и дедупликацию.

Если публичный endpoint webhook недоступен, явно сообщить о препятствии для проверки входящих данных в реальной среде.

### 19.3 Проверка Google Calendar в реальной среде

При доступном Google OAuth проверить как минимум:

- реальное подключение OAuth;
- реальное создание тестового события;
- сохранённый идентификатор события провайдера;
- пригодный внешний URL, когда его предоставляет провайдер;
- как минимум одну реальную проверку обновления/отмены.

### 19.4 Проверка WhatsApp в реальной среде

Выполнять проверку в реальной среде только при фактическом наличии валидной конфигурации Meta Business / Cloud API.

При недоступности допустим следующий явно указанный статус:

```text
IMPLEMENTED / NOT LIVE-VERIFIED — external provider setup required
```

Не помечать интеграцию проверенной в реальной среде, основываясь только на моках, тестах адаптера или вымышленных учётных данных.

Все проверки в реальной среде должны использовать синтетические/тестовые данные и очищать временные тестовые данные/артефакты провайдера там, где это практически возможно.

## 22. Критерии финального MVP

MVP Day 5 завершён при соблюдении следующих критериев:

1. утверждённая функциональность интеграций реализована согласно этому контракту;
2. авторизация бэкенда проверена;
3. секреты провайдеров не раскрываются через исходный код, журналы, ответы API, браузерный UI, тесты или отчёты;
4. идемпотентность предотвращает дублирующее создание Communication для повторных фактов провайдера;
5. EmailDraft отправляется только явным действием сотрудника и после подтверждённой отправки становится неизменяемым/копируемым;
6. Task и CalendarEvent остаются отдельными, но могут быть явно связаны;
7. отключённые/деградировавшие провайдеры не нарушают обычную работу CRM;
8. присутствуют требуемые пользовательские строки RU/EN/ES;
9. миграции PostgreSQL и релевантные автоматические тесты проходят;
10. production-сборка фронтенда и релевантный браузерный smoke-тест проходят;
11. каждый реальный провайдер либо фактически проверен в реальной среде, либо явно документирован как не проверенный в ней из-за конкретного внешнего препятствия;
12. документация — источник истины точно отражает то, что было фактически проверено.

## 23. Архитектурные решения, зафиксированные этим контрактом

- Одно корпоративное подключение на провайдера для MVP.
- Gmail + Google Calendar используют Google OAuth.
- Runtime OAuth-токены Google шифруются на уровне приложения до сохранения в PostgreSQL; ключ шифрования остаётся только секретом окружения/развёртывания.
- Статические учётные данные Telegram/WhatsApp для MVP передаются через секреты окружения/развёртывания.
- Только ADMIN управляет подключениями интеграций.
- Вызовы провайдера проходят через адаптеры/сервисы.
- Жизненный цикл провайдера сообщений сохраняется в `ExternalMessage`; историей CRM остаётся `Communication`.
- `Communication` создаётся только для фактических подтверждённых исходящих или принятых/сопоставленных входящих фактов коммуникации.
- Несопоставленный входящий трафик не создаёт Clients автоматически.
- Корреляция Gmail Deal может использовать детерминированную историю треда провайдера; угадывание AI/по тексту запрещено.
- `Task != CalendarEvent`; утверждена необязательная явная связь.
- Calendar не становится полноценным приложением календаря CRM.
- EmailDraft после подтверждённой успешной отправки становится доступным только для чтения, но копируемым.
- Celery/Redis используются повторно; логическая очередь интеграций разрешена без новой инфраструктуры брокера.
- Исходящее состояние `UNKNOWN` предотвращает небезопасные слепые повторы после неопределённого результата провайдера.
- Отключение никогда не удаляет исторические записи CRM/провайдера.
- Проверка WhatsApp в реальной среде зависит от реальной настройки Meta и может честно документироваться как внешне заблокированная.
